Downloads

whole Books onto the device, through one background session that survives kills and reboots

Logos plays from local files only, so a Book must be downloaded before it can be played. This module does that: it fetches every audio file of a Book plus its cover, checks each file, and only then marks the Book downloaded. A Download is all or nothing: a Book with one missing file is not downloaded.

In the The module graph Downloads may use Domain, ServerAPI (for Auth, the Book data request and the file transfer seam FileTransfers) and Store. Like Sync, it never talks to the UI directly: it writes each Download's state into the database, and the Downloads screen observes it (The database is the single source of truth).

The heart of the module is one actor, Downloader. Its queue lives in the database, not in memory, so it survives a force-quit, a crash or a reboot. The actual bytes travel through an iOS background URL session (wrapped in ServerAPI as BackgroundFileTransfers.swift), which keeps transferring while Logos is suspended or even not running, and relaunches Logos in the background when transfers finish (Apps in the background, Journey: downloading a Book).

iOS & Swift

A background URLSession hands transfers to a system process. Your app can be suspended or killed and the transfers carry on; when they finish, iOS launches the app in the background and calls application(_:handleEventsForBackgroundURLSession:completionHandler:) on the app delegate. That's why LogosApp.swift creates the transfers object as early as possible and starts the Downloader even without any UI.

The other files are small: management (reorder, the launch file check), sign-out, and two seams — protocols with a real implementation and room for a fake in tests — for the network type (NetworkMonitor) and free disk space (StorageCapacity).

Who calls Downloads? LogosApp.swift builds one Downloader per signed-in identity, sharing that identity's Auth. In UI, DownloadsModel.swift and DownloadsModel+Manage.swift call download, cancel, reorder, resume, enteredBackground and checkFiles, and RootView.swift runs the file check after the first frame.

LogosKit/Sources/Downloads/Downloader.swift

519 lines · GitHub

The Downloads engine. Read the long doc comment at the top first: it is the specification of every failure rule, and the code below implements it rule by rule.

Annotated source

The rules, in short:

  • One Book at a time, first in first out. Each file is one transfer, enqueued from the foreground when the Book becomes active.
  • A file is verified when the Server answered 200 or 206 and the size on disk equals the size the Server reported.
  • Before enqueueing, the token is refreshed if it has less than 10 minutes left (background transfers carry the token in their request and can't refresh it themselves), and the Book's data is re-read, because a file's ino (its ID on the Server) can change.
  • 401 → refresh and retry that file, not counted as an attempt. 403 → the Book fails. 404 → re-read the Book and retry once. Wrong size → delete and refetch once. Anything else → retry after a backoff of about 1, 5 then 30 minutes, at most 5 attempts.
  • Not enough free space pauses the queue instead of failing.
  • Wi-Fi only unless the listener allows cellular.
House rule

ADR 0001 ("the database is the single source of truth") is why the queue lives in the Store. The Store's download and downloadFile tables hold each Book's state, each file's received bytes, attempts and resume data, so resume() can rebuild everything from them.

advance() is the queue loop: while there's room on disk, ask the Store for the next Book to start and enqueue its missing files. It stops as soon as one Book is in flight or waiting; finished, failed or cancelled Books let it move on to the next one.

The storage check. The Book about to start (or the active one, if the queue is already paused for storage) must fit, with a 500 MB margin. The pause is recorded in the Store, so the UI can show "Not enough storage", and lifted once there's room.

transferMissingFiles(of:) is the core step. In order:

  • Get a token valid for at least 10 more minutes, and re-read the Book's data from the Server. A 404 or 403 here means the Book is gone: fail it.
  • A Book with no audio tracks fails.
  • Fetch the cover if needed (it is part of the Download).
  • Save the fresh Book data and the list of files to the Store.
  • For each file not yet verified and not already running or backing off: if the full file is already on disk (it arrived just before a kill, before it could be recorded), mark it verified; otherwise enqueue a transfer, passing any resume data so it continues where it stopped.
  • If everything is verified, finish the Book.
Why it is like this

Files are keyed by relPath (their path inside the Book) rather than ino, because the Server's ino can change; that's why the Book data is fetched again before every enqueue.

Events from the background session: progress, finished, or failed. A failed transfer keeps its resume data. If the disk can't hold the rest, that's not a network failure, so the queue pauses for storage instead of using up an attempt.

A transfer finished with an HTTP status. This switch is the failure rules from the top of the file, almost word for word: verify the size on 200/206, refresh on 401, fail on 403, retry once on the first 404, fail on the second, and back off on anything else.

A transfer that finishes for a Book that was cancelled meanwhile has its file deleted, so nothing is left behind.

Backoff. The attempt is counted and saved, then a task sleeps on the injected Clock and re-enqueues the file. The due time is computed before the task starts, so a slow start doesn't stretch the wait.

House rule

Never Task.sleep directly in Downloads: sleep on the Clock. In tests, TestClock advances time instantly, which is how the 1/5/30-minute backoffs are tested without waiting (Seams: how the code is made testable).

A protocol lists what a type must provide, like an interface in other languages. Code depends on the protocol (any NetworkMonitor), so tests can pass a fake that yields whatever they want. : Sendable requires every implementation to be safe to share between actors.

The real implementation wraps Apple's NWPathMonitor (from the Network framework) in an AsyncStream. A path counts as Wi-Fi when it's usable, not in Low Data Mode, and over Wi-Fi or wired Ethernet. When the reader stops listening, onTermination cancels the monitor.

Many older Apple APIs call you back on a closure (pathUpdateHandler). Wrapping them in AsyncStream { continuation in ... } turns those callbacks into something you can for await over, which is the shape the rest of this codebase uses.

Tests

how Logos proves itself: unit tests per module, integration tests against a real Server in Docker, and XCUITest on the app

Logos has three kinds of tests, each with its own tool and its own way to run. Almost all of them are unit tests, one test target per module. A smaller set of integration tests talks to a real audiobookshelf Server running in Docker on your Mac. On top of those, a handful of UI tests launch the real app and tap through it the way a person would.

iOS & Swift

Swift Testing vs XCTest. Apple ships two test frameworks. XCTest is the old one: a test is a method whose name starts with test on a subclass of XCTestCase, and you check things with XCTAssertEqual(a, b) and friends. Swift Testing (import Testing) is the new one: any function marked @Test("a sentence") is a test, a type marked @Suite groups them, and one macro, #expect(a == b), covers every check. When it fails, it prints both sides of the expression. try #require(x) unwraps an optional or stops the test. @Test(arguments: [...]) runs one test once per input (a parameterized test). Swift Testing creates a fresh instance of the suite struct for every test, so properties set in init() act as per-test setup, with nothing shared between tests. Logos writes every unit and integration test in Swift Testing. It uses XCTest only where it has to: XCUITest, the part of XCTest that drives a running app from outside, and the performance metrics (measure(metrics:)), which only XCTest has.

How the unit tests are organised. Each module X in LogosKit/Sources/X has a target XTests in LogosKit/Tests/XTests, declared in LogosKit/Package.swift. One file covers one behaviour or one type, and the @Test names are full sentences that read like a spec ("An empty list is never applied"). The targets:

  • DomainTests: pure logic with no I/O, such as title sorting, Series order, the Finished rule, the Sleep Timer, Listening session splitting, playback times, the fixture Library generator and TestClock itself. These tests barely need helpers because the code under test is just values and functions.
  • ServerAPITests: building HTTP requests, and decoding responses from JSON payloads recorded from a real audiobookshelf 2.37.1 (Tests/ServerAPITests/Payloads/*.json, bundled as test resources). Also Auth (token refresh, sign-in state) and TokenStore. Helpers: TestJWT, FakeServer, TestClock.
  • StoreTests: the GRDB database, one file per store (Library, Progress, Downloads, Series, Outbox, sign-out…), plus migrations and observation. Every test opens a real SQLite file in a fresh temporary directory. Shared builders: listedBook(_:) (in StoreTests/LibraryStoreTests.swift) and bookData(_:) (in StoreTests/BookDataStoreTests.swift).
  • SyncTests: sign-in, the Library sync, Book data, covers, progress, the Outbox, Finished changes and "needs sign-in". Built on SignedInFixture (in SyncTests/LibrarySyncTests.swift): a FakeServer, a TestClock, an InMemoryTokenStore and a real database, already signed in. Other files add to it through extension SignedInFixture.
  • DownloadsTests: the download queue, retries and backoff, failures, storage and network rules, managing Downloads, and sign-out. Built on DownloadsFixture (in DownloaderTests.swift), which adds FakeFileTransfers, a FakeStorageCapacity, and real Downloads/ and Covers/ folders.
  • PlaybackTests: the Player engine (play, seek, Chapters, settings, Finished, damaged Downloads, pick-up, sessions, the Sleep Timer) and Now Playing (lock screen). Built on PlayerFixture, which uses FakeAudioPlayer and FakeAudioSession so no sound is ever made. SystemAudioPlayerTests covers the real AVPlayer wrapper.
  • UITests: the @MainActor screen models in the UI module (Library, search, Book detail, Series, Downloads, In Progress, sign-in and sign-out, the listening reporter, notices). It doesn't test SwiftUI views. The models are built on the real Store and Sync over a FakeServer; FakeConnectivity, FakeBackgroundTasks and FakeNetwork are local test doubles. Don't confuse this target with LogosUITests: UITests tests the UI module in Swift Testing, while LogosUITests drives the app with XCUITest.
  • IntegrationTests: ServerAPI, Sync and Downloads against the Docker Server (Integration tests (against a real Server)).
  • Each module also has a tiny LogTests.swift that checks the module's log category.

The testing philosophy. Every boundary the code can't control in a test is a seam: a protocol in the production code with a real implementation and a fake one (Seams: how the code is made testable). The fakes live in the production modules, not in the test targets: FakeServer.swift (the fake ServerAPI), FakeFileTransfers.swift (background downloads), FakeAudioPlayer.swift (AVPlayer), InMemoryTokenStore (the Keychain) and TestClock.swift (time). That way every test target can use them, and so can the app's own test launches in TestLaunch.swift. Everything else stays real: the database is a real SQLite file and Downloads go into a real temporary folder. Tests mock as little as possible and assert on what ends up in the database or on disk, because the database is the single source of truth (The database is the single source of truth).

House rule

Never call Date() or Task.sleep in Sync, Downloads or Playback: inject a Clock. In tests this is TestClock, so "15 minutes later" is await clock.advance(by: .seconds(15 * 60)), which runs instantly and gives the same result every time.

Running them.

  • scripts/test.sh builds the app and runs every unit-test target on the simulator through the Logos scheme (DEVICE picks the simulator, default iPhone 18 Pro). Narrow it with xcodebuild's -only-testing:: scripts/test.sh -only-testing:SyncTests, -only-testing:SyncTests/LibrarySyncTests, or one test with -only-testing:SyncTests/LibrarySyncTests/applies(). CI runs this on every PR.
  • scripts/integration-test.sh starts audiobookshelf in Docker, seeds it, runs IntegrationTests and tears it all down. Append -only-testing:IntegrationTests/HarnessTests to narrow it. It needs Docker and isn't run in CI. A PR touching ServerAPI or Sync attaches its result.
  • scripts/integration-test.sh --ui runs the app's smoke test (LogosUITests/SmokeTests) against the same Docker Server instead. --serve only starts and seeds the Server, so you can sign in to it by hand from the simulator.
  • Performance tests: the LogosPerformance scheme, on a real iPhone, by hand (Performance budgets and docs/performance-budgets.md). scripts/perf-results.sh <result>.xcresult prints medians and worst runs.
  • In Xcode, ⌘U runs the selected scheme's tests, and the diamond next to a @Test runs just that one.
Why it is like this

The integration tests sit outside the Logos scheme because they need Docker and a running Server. When the harness isn't configured, they skip (.enabled(if: IntegrationServer.isConfigured, …)), so scripts/test.sh and CI stay green without Docker. scripts/integration-test.sh fails if anything was skipped, so a real run can't pass silently.

The core promise: a sleeper wakes exactly at its deadline. The test starts a Task that sleeps 60 s, advances 59 s and checks the task hasn't woken, then advances 1 s more. try await sleeper.value waits for the task to finish (and rethrows its error, if any).

Why it is like this

The comment explains a real pitfall. The engine starts its own main-actor tasks, and when other tests keep the main actor busy, a single clock tick isn't enough for them to run.

UI: book, player & downloads

Book detail, the Downloaded tab, the mini-player and player sheet, and listening reporting

This page is the second half of the UI module. The first half (RootView.swift and friends) is the app shell and the browsing tabs; this half is everything that happens once the listener picks a Book: its detail screen, downloading it, playing it, and telling the Server what was listened to.

UI sits at the top of the module graph (The module graph): it may import Domain, Store, Sync, Downloads and Playback, and nothing imports it. The files here lean on three objects from lower modules: the AppDatabase (from Store), the one Player (from Playback) and the Downloader (from Downloads). The app target builds those once and hands them in (The composition root and launch).

The pattern is the same on every screen. A model class (BookDetailModel, DownloadsModel) is marked @Observable, reads its first values synchronously from the database in init so the very first frame has real content, and then follows the database with an observe() method that a view runs in .task. A view struct reads the model and calls its methods. Background work (Downloader, LibrarySync) never calls the UI back; it writes to the database, and the models notice (The database is the single source of truth).

The Player is the exception: it is @Observable itself and the player views read it directly (its position changes several times a second, too often to go through the database). It is put into the SwiftUI environment once by PlayerChrome.swift, and so is the shared DownloadsModel, so any view deep in the tree can pick them up with @Environment.

iOS & Swift

SwiftUI in one paragraph. A screen is a struct conforming to View with a body property that describes the UI. You never mutate on-screen widgets; you change state, and SwiftUI calls body again and diffs the result. VStack/HStack stack children vertically/horizontally, List is a scrolling table, and chained calls like .font(.headline) are modifiers that wrap a view in another view. See SwiftUI: describing the screen.

House rule

ADR 0001: the database is the single source of truth. A model never gets pushed state by Sync or Downloads; it observes the Store. If you add a screen, copy the shape of BookDetailModel: read in init, follow in observe().

The picker: preset buttons, a slider with − and + buttons for fine steps. Each change calls player.setSpeed, which also saves it.

Why it is like this

Speed changes sound natural thanks to the player's time-domain pitch algorithm (AVAudioTimePitchAlgorithm.timeDomain, Apple's speech algorithm, set in SystemAudioPlayer.swift:57); this view doesn't need to know about that.

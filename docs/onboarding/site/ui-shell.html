UI: shell & browsing

SwiftUI screens, their @Observable models, and how they follow the database

UI is the module the listener actually sees: the sign-in screen, the four-tab shell (In Progress, Library, Series, Downloaded), Settings and every list and row. This page covers the shell, sign-in and sign-out, Settings and the browsing screens. The rest of UI (Book detail, the player, the Downloads tab and the listening reporter) is on the next page.

UI sits at the top of the The module graph: it may use Domain, Store, Sync, Downloads and Playback, and nothing depends on UI. It never talks to ServerAPI directly; anything that needs the network goes through a Sync or Downloads object that the app target hands in. The app target (LogosApp.swift) builds one AppRootView and passes it the database, the sign-in service and factory closures for the per-identity objects. That is the only door into the module.

iOS & Swift

SwiftUI is Apple's declarative UI framework. A screen is a struct that conforms to View and has a body property describing what to show for the current state. You never "update a label"; you change state, and SwiftUI calls body again and works out what changed on screen. Chained calls such as .navigationTitle(…), .toolbar { … } and .task { … } are view modifiers: each wraps the view in another one with an extra behaviour. See SwiftUI: describing the screen.

Almost every screen here comes as a pair: a model (LibraryModel, SignInModel, SettingsModel, …) and a view (LibraryView, SignInView, SettingsView, …). The model is a class marked @Observable that holds the screen's state and does its work: reading the Store, starting a sync, saving a setting. The view is a thin struct that draws the model's properties and calls its methods. Models are public so the test target UITests can drive them without any SwiftUI; most views are internal (no access keyword), since only this module shows them.

iOS & Swift

@Observable (from the Observation framework) turns a class into something SwiftUI can watch. When body reads model.sections, SwiftUI remembers that, and when sections changes later, that view is redrawn. Nothing else is needed: no publishers, no objectWillChange. Properties marked @ObservationIgnored aren't tracked: use that for internal bookkeeping that should never cause a redraw. See @Observable models.

The models follow ADR 0001, The database is the single source of truth: Sync, Downloads and Playback only ever write to the database, and never call back into UI. Each model reads its data once, synchronously, in init (so the very first frame already shows real rows), then calls a Store …Updates() method in its observe() method and loops over the resulting AsyncThrowingStream. That stream is backed by GRDB's ValueObservation, which runs the query again after every write that could change its answer (AppDatabase.swift:94). A view starts that loop with .task { await model.observe() }; SwiftUI cancels the task when the view goes away, which ends the loop.

iOS & Swift

UI (like Playback and the app) is compiled with main-actor isolation by default (.defaultIsolation(MainActor.self) in Package.swift). Every type and function in this module runs on the main thread unless it says otherwise, which is exactly what UI code needs: it may touch views and @Observable state freely. Heavy work is pushed off the main thread on purpose, with Task.detached or a @concurrent function, and anything that must run off it is marked nonisolated. See async/await and tasks and Actors, the main actor and Sendable.

Navigation is plain SwiftUI. AppRootView chooses between sign-in and the shell. The shell, RootView, is a TabView with one NavigationStack per tab, so each tab keeps its own back stack. Screens push Book detail and Series pages with .navigationDestination(item:): setting an optional @State value to non-nil pushes the destination, and going back sets it to nil again. Settings and "sign in again" are sheets (cards that slide up over everything), and the player sits along the bottom as a tab-view accessory (PlayerChrome.swift, on the next page).

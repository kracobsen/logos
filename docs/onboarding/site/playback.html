Playback

the engine that plays a downloaded Book, and everything the system does to it

Playback is the audio engine of Logos. It plays exactly one downloaded Book at a time, from the files of its Download on the phone's disk, and never from the network. It keeps the position, the current Chapter, the speed, the Sleep Timer and Finished up to date; it saves the position to the database; and it reacts to what iOS does to the app's audio (a phone call, unplugged headphones, the car disconnecting). It also publishes the loaded Book to the lock screen and Control Center and turns their buttons into player actions.

In the The module graph Playback may depend only on Domain and Store. In particular it may not import ServerAPI: it physically can't reach the Server. Everything it learns about the outside world comes through the database (Store), and everything it tells the outside world it writes to the database or announces through a stream of "playing stopped" events that the UI module's ListeningReporter uses to send Listening sessions.

House rule

CLAUDE.md: Playback must never import ServerAPI, and scripts/check-module-graph.sh fails CI if it does. Playback (like UI and the app) is compiled with @MainActor as the default isolation, so all its code runs on the main thread unless it says otherwise. It also must not call Date() or Task.sleep directly: time comes from the injected Clock (see Seams: how the code is made testable).

The key types:

  • Player (Player.swift plus the Player+*.swift extensions): the engine and its rules. One instance for the whole app, made in the composition root (LogosApp.swift).
  • AudioPlayer (AudioPlayer.swift): a small protocol, the seam between the rules and Apple's AVPlayer. SystemAudioPlayer is the real implementation, FakeAudioPlayer the scripted one tests use.
  • AudioSession (AudioSession.swift): the seam for system audio events (interruptions, route changes, media-services resets). SystemAudioSession is real, FakeAudioSession is for tests.
  • NowPlaying (NowPlaying.swift): keeps the lock screen and Control Center in step with the Player, through the NowPlayingCenter seam (NowPlayingCenter.swift); SystemNowPlayingCenter talks to iOS 27's NowPlaying framework.
Why it is like this

The pattern "rules in one class, thin protocols around every Apple API" runs through the whole module. Apple's audio classes can't be driven from a unit test (they need real time to pass, real hardware, real calls), so each one sits behind a protocol the engine talks to. Tests swap in a fake where nothing moves until the test says so, and can check every rule (finishing within the last 30 s, Sleep Timer stops, resuming after a call) deterministically and in milliseconds. See Seams: how the code is made testable.

Why it is like this

The live position is the one exception to "the database is the single source of truth" (The database is the single source of truth, ADR 0001). It changes several times a second, so the Player publishes it directly as an observable property, and writes it through to the database every second while playing and immediately on play, pause, seek, skip, Chapter jump, the end of the Book and going to the background.

How others use it: the UI observes Player's properties to draw the mini player and the player sheet, and calls play(bookID:), pause(), skip(by:) and so on (PlayerChrome.swift, PlayerViews.swift). The UI also starts three long-running tasks on it at launch: restoreLastPlayed(), observeDownloads() and observePickUps(). Sign-out calls signOut() then reloadSettings() (SignOutModel.swift). The ListeningReporter (ListeningReporter.swift) subscribes to stops() to send the Outbox when playing stops. For a narrative walk-through of pressing Play, see Journey: playing; for the AVFoundation basics, Audio: AVFoundation and Now Playing.

The heart of the module: the playback engine. It holds the state the screens show (what's loaded, where it is, whether it plays, what went wrong) and the rules for every control. It's long, so the rules for specific concerns live in extensions in other files (Player+AudioSession.swift, Player+PickUp.swift, Player+SleepTimer.swift and so on); this file has loading, the basic controls, the player's own reports and saving.

A useful mental model: Player never trusts AVPlayer's idea of time blindly. It keeps its own position (what the listener sees), moves it at once on a seek, and lets the audio catch up. A handful of counters (pendingSeeks, reloadsInFlight, loadGeneration) exist only to know when the audio's reports are stale and must be ignored.

The private machinery. @ObservationIgnored keeps these out of observation: they're implementation details, and changing them shouldn't redraw any view.

  • database (Store's AppDatabase) and files (where Downloads live on disk) are how the engine reads Books and saves progress.

load is the most careful function in the engine. In order:

  • Pause whatever is playing (reported as a Book switch), cancel any Sleep Timer, bump loadGeneration and clear old notices.
  • Read the Book and check its Download is complete (downloadStatus == .downloaded). Only a downloaded Book can be played, by definition of Download.
  • Check every file is on disk with the right size (hasIntactDownload). If not, the Download is damaged: it's discarded and the UI offers "Download again".
  • Publish the Book and its saved position at once (state .loading), so the UI can show it while the audio loads.
  • Ask the audio to load the files, then seek to the saved position.

After every await, guard generation == loadGeneration checks whether another load started meanwhile. If the listener tapped two Books quickly, the first load finishes second and must not overwrite the second Book. min(max(...)) clamps a saved position into the Book's length, in case the data is odd.

Play and the save loop. play() only works from .paused. start does the real work:

  • A Finished Book starts again from 0 and is no longer Finished (the glossary's definition of Finished).
  • It tells the audio to play, sets .playing, saves at once, and starts a loop that saves every second.

The loop sleeps through the injected clock, not Task.sleep, so tests can advance time by hand with TestClock. Each tick checks the Book is still playing (and is the same Book), skips saving while a reload is landing, reads the live time from the audio and saves.

Pause and finish. Every pause has a reason (PlaybackStop.Reason), which decides whether the listening session ends and is reported to observers.

The Finished rule: if the listener stops within the last 30 seconds of the Book, the Book becomes Finished instead (FinishRule.finishes in Domain). The system pausing (a call, unplugged headphones) never finishes a Book; that would be surprising.

pendingSeeks == 0 ? audio.currentTime : position is the stale-report guard again: if a seek hasn't landed, the audio's time is still the old one, so the engine's own position (the seek target) is the truth.

finish stops, marks Finished, moves to the end and saves. Nothing plays next; Logos has no queue.

Sync

keeping the device and the Server in step: sign-in, the catalogue, progress and the Outbox

Sync is the module that talks to the Server on the app's behalf for everything except file Downloads. It signs in, keeps the local copy of the Library up to date, picks up listening progress made on other devices, and sends what this device has recorded (its Outbox) back to the Server.

In the The module graph Sync sits in the middle: it may use Domain (the shared types), ServerAPI (the HTTP calls and Auth, the token keeper) and Store (the GRDB database). It never imports UI, and UI never gets data from Sync directly. Instead Sync writes to the database, and the screens observe the database (see The database is the single source of truth). Most functions here therefore return a small outcome enum that says how a run went, not the data itself.

The key types:

  • LibrarySync: the catalogue sync, in three stages (the Library list, then full Book data, then covers). It also owns the other three long-lived Sync objects for a signed-in identity, so the app builds one LibrarySync and reaches the rest through it.
  • ProgressSync: fetches GET /api/me/progress and merges it into the Store.
  • SessionOutbox: sends Listening sessions and Finished changes to the Server and confirms what it accepted.
  • Connection: whether the listener needs to sign in again or the Server is too old, as a stream the UI can watch.
  • SignIn: the sign-in flow itself (see Journey: signing in).

Almost everything here is an actor. That keeps the network and database work off the main thread, and lets a trigger that arrives while a run is in progress join that run instead of starting a second one. The same pattern (if let running { return await running.value }) shows up in LibrarySync, ProgressSync and SessionOutbox.

House rule

Sync never throws to the UI and never retries on a timer of its own. Failures are logged and reported as an outcome; the next trigger (launch, return to the foreground, Refresh, a minute of playback, the network coming back) simply tries again. Sync code also never calls Date() or Task.sleep: it uses the injected Clock from Domain so tests can control time (Seams: how the code is made testable).

Who calls Sync? The app's composition root (LogosApp.swift) builds a LibrarySync per signed-in identity. In UI, LaunchModel.swift and RootView.swift trigger syncs, ListeningReporter.swift drives the Outbox while a Book plays, BookDetailModel.swift asks for one Book's full data straight away, and SignOutModel.swift sends the Outbox one last time before signing out.

Two small enums describe a sync from the outside: what started it (SyncTrigger) and how it ended (SyncOutcome). The UI uses the outcome to decide what to say, for example a "can't reach the Server" message or the needs-sign-in banner.

iOS & Swift

A Swift enum lists a fixed set of cases. A case can carry values ("associated values"), like serverTooOld(found: String), which carries the version the Server reported. Sendable promises the value can safely cross between threads/actors; Hashable lets it be compared and used in sets. Swift 6 strict concurrency (this repo's setting) refuses to pass non-Sendable values between actors, so almost every Domain-ish type here says Sendable.

The comment on SyncOutcome matters: only .synced means something was written. Every failure leaves the Store exactly as it was.

The class doc sums up the whole sync. Note the four nonisolated let properties: clock, progress, outbox and connection. They are made once in init and never change, so they can be read from outside the actor without await.

iOS & Swift

An actor is like a class whose state can only be touched by one task at a time; calling into it from outside needs await, because you may have to wait your turn. nonisolated opts a member out of that protection, which is safe only for constants that are themselves Sendable.

Why it is like this

Bundling ProgressSync, SessionOutbox and Connection inside LibrarySync means they all share one Auth for the identity. That gives one token refresh shared by everything, rather than several parts of the app racing to refresh the same token (the comment in LogosApp.swift says the same about Auth and Downloads).

Why it is like this

LogosKit/Sources/Sync/LibrarySync+BookData.swift

71 lines · GitHub

Stage 2 of the sync: the full data of each Book (description, Chapters, audio tracks, Series membership). The Library list from stage 1 is cheap and small per Book; this is the expensive part, so it's done only for Books the Store marks as "behind".

Annotated source

Books behind on full data are fetched 50 at a time with audiobookshelf's batch endpoint, and each batch is saved in its own transaction. An interrupted sync therefore loses at most one batch: the next sync asks the Store again which Books are still behind and carries on.

A batch the Server rejects is skipped; an unreachable Server stops the stage but keeps stage 1's outcome; only a rejected sign-in changes the overall outcome.

iOS & Swift

stride(from:to:by:) counts 0, 50, 100, … ; behind[start..<end] takes a slice of the array. catch AuthError.needsSignIn matches one specific case of the error enum.

withTaskGroup runs child tasks concurrently and lets you collect their results with await group.next() as each one finishes. It's structured concurrency: the group doesn't return until every child is done (or cancelled with cancelAll()).

Why it is like this

The class doc is the best summary of the Outbox rules:

  • The Outbox lives in the Store, not in memory, so a kill or reboot loses nothing.
  • This actor deletes nothing itself; the Store confirms each accepted session at the revision that was sent. If the session changed again meanwhile (playback went on), it stays unsent and goes out next time.
  • A Book whose session the Server rejected is skipped until the next catalogue sync, so one bad Book can't block the rest.

rejectedBooks remembers those Books in memory, together with the catalogue sync time at which they were rejected.

The Finished part of the Outbox. When the listener marks a Book Finished (or not) by hand, the Store queues a Finished change stamped with the time they did it. This file sends those with PATCH /api/me/progress/:id, carefully, so a change never overwrites something newer made on another device.

The main flow:

  • /status: is it reachable, is it ≥ 2.36, and does it allow username/password sign-in?
  • POST /login: get the token pair and the user.
  • The Library list, keeping only book Libraries (podcasts are hidden).
  • None → error; exactly one → picked automatically; several → return .chooseLibrary and let the UI ask.

Whenever sign-in gives up after a successful login, it logs that login out again on the Server so no session is left dangling.

isSameServer compares URLs loosely enough (host case, default port, trailing slash) that a listener retyping their address doesn't get "different Server". choose finishes a sign-in: tokens first, then the identity.

Why it is like this

Order matters: the identity is saved last because its presence is what tells launch "signed in". If saving the tokens failed, there must be no identity pointing at missing tokens.

Store

the GRDB database, the single source of truth, and the files on disk

Store is where everything Logos knows is kept: the Library list, each Book's Chapters and tracks, progress, the Download queue, the Outbox, settings and the signed-in identity. It owns one SQLite database, opened through the third-party library GRDB, plus two small helpers for files on disk (covers and Download audio).

In the module graph Store sits right above Domain: it may import only Domain and GRDB, and it is the only module allowed to import GRDB. Sync, Downloads, Playback and UI all depend on Store, and talk to the database exclusively through the methods on AppDatabase — they never see a GRDB type or write SQL themselves. See The module graph.

House rule

ADR 0001: the database is the single source of truth. Sync, Downloads and Playback write here and never call back into the UI; each screen's model observes the database and redraws when the rows it reads change. If you are tempted to add a shared in-memory cache that the UI reads, don't: put it in a table and observe it. See The database is the single source of truth.

How the module is organised. There is one public type, AppDatabase (AppDatabase.swift), a small struct wrapping a GRDB DatabasePool. Every other file is an extension AppDatabase that adds the methods for one area (Library, progress, Downloads, sessions…), and usually also registers the migration that creates that area's tables. Reads come in pairs: a plain foo() that reads once, and a fooUpdates() that returns an AsyncThrowingStream yielding the value now and again after every relevant change. Both share one static func fetchFoo(_ db:), so the one-shot read and the live read can never disagree.

iOS & Swift

GRDB in five ideas. (1) A DatabasePool is a set of SQLite connections: one writer and several readers, in WAL mode, so reads never wait for writes. It is Sendable (safe to share between threads). (2) pool.read { db in … } and pool.write { db in … } run a closure on a connection; every write is one transaction: all of it commits or none of it does. (3) A record is a Swift struct that conforms to FetchableRecord (can be built from a row) and PersistableRecord (can be inserted/updated/upserted); with Codable GRDB maps properties to columns by name. (4) A migration is a named, numbered step that changes the schema; DatabaseMigrator runs the ones not yet applied, in order, and remembers them in a grdb_migrations table. (5) A ValueObservation re-runs a fetch whenever a transaction commits a change to any table that fetch read from, and delivers the new value. See SQLite and GRDB.

The schema at a glance. All tables are created by migrations in this module:

  • serverIdentity (one row, id 1) — which Server, user and Library Logos is signed in to. Its presence means signed in.
  • syncState (one row) — when the Library list was last applied, and the last "Server too old" version.
  • book — one row per Book: the list columns sync stage 1 writes, the fullDataVersion/coverVersion bookkeeping for stages 2 and 3, and the notOnServer flag.
  • chapter, audioTrack, bookSeries — stage 2's per-Book data, deleted with the Book (ON DELETE CASCADE).
  • progress — one row per Book: position, Finished, and when the listener acted. Deliberately not tied to book.
  • download, downloadFile — the Download queue (state and order) and each Download's files with their transfer state.
  • downloadPolicy, playbackSettings — one-row settings tables; "no row" means defaults.
  • listeningSession, finishedChange — the Outbox: Listening sessions and Finished changes waiting for the Server.
  • clientDevice — the id this install reports to the Server as its device.
Why it is like this

Times are stored as integer milliseconds (ms since 1970) wherever they are compared with the Server's timestamps (updatedAt, lastChanged, lastUpdate), because that's what the Server sends, so "is the Server's change newer than mine?" is an exact integer comparison. A few purely local times (lastLibrarySync, completedAt) are seconds as Double.

Files on disk. Covers and Download audio don't go in the database; CoverFiles and DownloadFiles know where they live. The database records which version or whether verified, and the launch file checks (CoverStore.swift, DownloadFileCheck.swift) reconcile the two after a restore from backup.

observe turns a fetch closure into an AsyncThrowingStream. ValueObservation.tracking(fetch) records which tables and rows the fetch reads; after any committed write touching them it runs the fetch again. removeDuplicates() drops results equal to the last one (hence Equatable), so a write to an unrelated column of the same table doesn't make the UI redraw.

iOS & Swift

async/await and AsyncSequence. for try await value in values loops over values that arrive over time; the loop suspends between them without blocking a thread. An AsyncThrowingStream is a hand-made async sequence: the continuation is how you push values into it. A Task { … } starts concurrent work; onTermination cancels that task when the consumer stops listening (e.g. a screen goes away), so observations don't leak. See async/await and tasks.

iOS & Swift

Generics. observe<Value: Sendable & Equatable> works for any Value type that is both Sendable and Equatable. @escaping @Sendable says the closure is stored for later and may run on another thread.

Wrapping GRDB's own values(in:) sequence in a standard Swift stream means callers outside Store never see a GRDB type.

Broadcast fans one value out to every current listener. Each stream() call registers a continuation; when that listener goes away its continuation is removed.

Domain

The shared vocabulary: plain value types and pure rules every other module builds on

Domain is the bottom of the module graph (The module graph). It imports only Apple frameworks (Foundation, os, Synchronization) and every other module may import it. Nothing in here talks to the network, the database, the audio hardware or the screen. What is left is the language of the app: the types that name the things in the Glossary's sense (Book, Chapter, Download, Listening session, Finished change …) and the small rules that decide things about them ("does stopping here make the Book Finished?", "does the Server's progress win over ours?", "which Book does the Series page's Continue button point at?").

Because those rules are pure functions over plain values, they are the easiest code in the repo to read and to test: DomainTests exercises them without a simulator-only dependency, a database or a fake. When a decision is made in one place and used by several modules, it lives here. For example the 30-second Finished window (FinishRule.swift) is used by Playback, and the last-writer-wins comparison (Progress.swift) by Store's progress merge.

The file groups you will find below, in reading order:

  • Seams: the Clock protocol with SystemClock and TestClock, plus Diagnostics (loggers) and Signposts (performance-budget markers). These are the "shared seams" CLAUDE.md talks about (Seams: how the code is made testable).
  • What the Server tells us: ServerIdentity, ListedBook (sync stage 1), BookData with AudioTrack and SeriesMembership (sync stage 2), Chapter/ChapterList, FetchedProgress.
  • What screens show: BookDetail, LibraryRow and LibraryCatalog (the Library tab's in-memory sort, filter and search), SeriesSummary/SeriesPage, InProgressRow, DownloadRow/DownloadsList, PlaybackTimes, SignOutSummary.
  • Rules: FinishRule, ProgressMerge, FinishedChanges, ListeningSessions, SeriesOrder/SeriesContinue, TitleSort, SleepTimer, PlaybackSpeed.
  • Test data: FixtureLibrary, a deterministic made-up Library used by tests and performance launches.
iOS & Swift

Almost every type here is a struct (or an enum) rather than a class. A Swift struct is a value type: assigning it or passing it to a function copies it, so nobody else can change "your" copy behind your back. A class is a reference type: everyone holding it shares one object. Value types make data safe to hand between threads, which is why the Store can read a BookDetail on a background queue and give it to the UI on the main thread.

iOS & Swift

You will see Sendable, Hashable, Identifiable on nearly every type. These are protocols (Swift's word for interfaces) that the type promises to satisfy. Sendable tells the compiler the value is safe to pass between concurrent tasks; with Swift 6 strict concurrency (async/await and tasks) the compiler refuses to move non-Sendable values across threads. Hashable gives == and lets the value be a dictionary key or set member; SwiftUI also uses equality to skip redrawing unchanged views. Identifiable means "has an id", which SwiftUI's List and ForEach use to keep track of rows.

iOS & Swift

Every type and member is marked public. Each LogosKit module is a separate Swift module, and Swift's default access level (internal) is visible only inside its own module. Anything Store, Sync or UI need must be public. Struct initialisers are never public automatically, so each public struct spells out its public init(...) by hand. That's why so much of this module is boilerplate initialisers; skim past them.

House rule

Never call Date() or Task.sleep in Sync, Downloads or Playback. Take a Clock instead, and use TestClock in tests (CLAUDE.md, "Shared seams in Domain").

LogosKit/Sources/Domain/Clock.swift

47 lines · GitHub

The Clock seam: the one way Sync, Downloads and Playback learn the time or wait. Anything that depends on time (last-writer-wins timestamps, the 60-second session sends, the 10-minute listening-session gap, retry backoff, refreshing tokens ahead of expiry, the Sleep Timer) goes through this protocol, so tests can control time exactly with TestClock.swift.

Annotated source
iOS & Swift

A protocol lists requirements without an implementation, like an interface in Java or TypeScript. var now: Date { get } asks for a readable property. func sleep(for:) async throws is an asynchronous function: callers must await it, which suspends their task without blocking a thread, and it can throw (here a CancellationError when the waiting task is cancelled). See async/await and tasks.

Why it is like this

The doc comment names every timing behaviour in the app that depends on this seam. The point is testability: a test can say "advance 10 minutes" and check that a listening session ended, without waiting 10 real minutes.

1import Foundation23/// The Clock seam: the current wall-clock time, plus sleeping and timers.4///5/// Injected into Sync, Downloads and Playback so that last-writer-wins timestamps, the 60 s sends,6/// the 10-minute session gap, backoff, refreshing ahead of time and the Sleep Timer are all testable.7/// Use ``SystemClock`` in the app and ``TestClock`` in tests. timer(every:) is built once, on top of the two requirements, for every clock. It returns an AsyncStream<Date>, a sequence you consume with for await tick in clock.timer(every: .seconds(60)) { ... }. Inside, a Task loops: sleep one interval, then yield the current time. When the consumer stops iterating, onTermination cancels the task, the next sleep throws, and the loop ends.

iOS & Swift

An extension adds members to an existing type, here to every type that conforms to Clock (a "protocol extension"). Swift code is often split into a small core declaration plus extensions. You'll see the same pattern as files named Player+SleepTimer.swift, which are extensions of Player kept in their own file.

iOS & Swift

Task { ... } starts a new unit of concurrent work. Tasks support cooperative cancellation: task.cancel() doesn't stop the code by force. It sets a flag that Task.sleep and other suspending calls check, and they then throw CancellationError.

1617extension Clock {18    /// Ticks with the current time every `interval`, starting one interval from now,19    /// until the consumer stops iterating.20    public func timer(every interval: Duration) -> AsyncStream<Date> {21        AsyncStream { continuation in22            let task = Task {23                while true {24                    do {25                        try await sleep(for: interval)26                    } catch {27                        break28                    }29                    continuation.yield(now)30                }31                continuation.finish()32            }33            continuation.onTermination = { _ in task.cancel() }34        }35    }36}

The production clock. Task.sleep(for:clock: .continuous) uses the continuous clock, which keeps counting while the device sleeps (unlike .suspending). So a timer that was due while the phone was locked fires right away when the process runs again.

The test implementation of Clock. Time stands still until the test calls advance(by:). It sits in the sources (not in a test target) so every module's test target, and the app's test launches, can share it. FixtureLibrary and ServerAPI's FakeServer are kept in the sources for the same reason.

Annotated source
iOS & Swift

final class means no subclass can inherit from this class. The class keeps all of its mutable state (the current time and the list of sleeping tasks) inside a Mutex<State> from the Synchronization framework. withLock { ... } runs the closure while holding the lock. That is how a class with mutable state can still be Sendable (the protocol requires it): every access to that state goes through the lock.

The initial time defaults to the Unix epoch (1 January 1970). Tests usually pass a fixed date so their timestamps are easy to read.

sleep(for:) puts the caller into a dictionary of sleepers keyed by an id, with a deadline of now + duration. It then suspends on a continuation until advance resumes it. If the task is cancelled while it waits, the onCancel handler takes the sleeper out and resumes it with CancellationError, just as a real Task.sleep would.

iOS & Swift

withCheckedThrowingContinuation connects callback-style code to async/await. The task suspends and is handed a continuation object. Calling continuation.resume() (or resume(throwing:)) exactly once wakes the task up. You'll meet the same tool wherever the app wraps an Apple callback API.

The (any Error)?? double optional encodes three outcomes from inside the lock: .none (really sleep), .some(nil) (resume now, the duration was zero), .some(error) (throw now, the task was already cancelled). The continuation is resumed outside the lock, which avoids running other code while holding it.

advance(by:) steps through the sleepers' deadlines in order. It sets now to the earliest due deadline, wakes those sleepers, lets them run, and repeats until it reaches the target time. Because of this, advancing by 3 minutes makes a 1-minute timer tick three separate times, each time with the correct now, rather than once.

settle() yields a hundred times. That's a pragmatic way to let freshly woken (or freshly started) tasks run until they suspend again, so that when advance returns, the code under test has reacted.

Annotated source

iOS & Swift

App target & tooling

the composition root, the build settings, and the scripts that guard the repo

Everything in LogosKit/ is a library: seven modules that know how to talk to a Server, keep a database, download and play Books, and draw screens. None of them can run by itself. This page covers the small layer that turns those libraries into an app you can install on an iPhone, plus the configuration and scripts around it.

The app target in Logos/ holds three Swift files. LogosApp.swift is the composition root: the one place where concrete objects are created and handed to each other (see The composition root and launch). LaunchEnvironment.swift decides where data lives and which Server API and token store to use. TestLaunch.swift adds fake environments for UI and performance tests, and is compiled only into builds that ask for it.

Package.swift declares the modules and the edges between them (see The module graph). The Config/ folder holds every build setting in plain-text .xcconfig files, plus Info.plist and the entitlements. The Xcode project file itself holds no build settings, so a change to how the app builds is a readable diff in Config/, not a hunk in project.pbxproj.

Last come the scripts in scripts/ and the CI workflow that runs them on every pull request: formatting, the module-graph check, the unit tests, and (run by hand, with Docker) integration tests against a throwaway audiobookshelf Server.

iOS & Swift

Project, target, scheme, configuration. An Xcode project (Logos.xcodeproj) is a container. A target is one thing it builds: here the Logos app and the LogosUITests UI-test bundle. A configuration is a named set of build settings (Debug, Release, and this repo's Performance). A scheme says which targets to build, run and test, and with which configuration for each action: the Logos scheme runs the Debug app and runs the LogosKit unit tests, LogosUITests runs the smoke test, LogosPerformance runs the performance tests in the Performance configuration. See Xcode projects, targets, schemes and configurations.

House rule

Structural changes (new modules, dependencies, edges) go in LogosKit/Package.swift, and build settings go in Config/*.xcconfig, never in the project file. The project file and schemes may show local changes when Xcode rewrites them; commit them only when you meant to change them.

The app's entry point and its composition root. It builds the long-lived objects once (database, sign-in, player, lock-screen integration, Downloads) and passes them into the UI's root view. @main marks the type the program starts from. Logos/LaunchEnvironment.swift

36 lines · GitHub

A small value describing where the app keeps its data and how it reaches Servers. A normal launch uses Application Support, the real HTTP client and the Keychain, and signs in over HTTPS only. Test builds can swap all of that out without the rest of the app noticing.

Annotated source
iOS & Swift

let declares a constant, var a variable. In a struct, let properties can't change after creation. The vars here have defaults, so a normal launch never sets them.

signedOut is a closure property: @MainActor () -> Void is "a function that takes nothing, returns nothing, and must run on the main actor". See Actors, the main actor and Sendable.

allowsPlainHTTPOnLoopback is the only way to sign in over plain http://, and only to 127.0.0.1/localhost: the UI smoke test's Docker Server.

Architecture

The modules and the rules between them, where state lives, and the main journeys through the code.

The seven modules

All the code except the app shell lives in the local Swift package LogosKit/, which has seven modules. Each module is a separate compilation unit with its own public interface:

Three rules matter most:

  • Playback never imports ServerAPI. The player physically can't reach the network, which is how the product rule "play only from Downloads" is enforced by the build. So how do listening sessions reach the Server? Playback writes them to the database, and ListeningReporter in UI asks Sync's SessionOutbox to send them. The data travels through the database, not through a call.
  • Only Store imports GRDB. Every other module sees AppDatabase methods that take and return Domain types. The record structs and SQL stay inside Store.
  • Nothing depends on UI. Sync, Downloads and Playback never call back into a screen. See the next section.
House rule

The graph is written down in three places that must change together: LogosKit/Package.swift (what the compiler enforces), scripts/check-module-graph.sh (what CI enforces), and the table in CLAUDE.md. Xcode builds every module into one directory, so a forbidden import can still compile. That is why the script also greps the imports ([[scripts/check-module-graph.sh]]).

The database is the single source of truth

This is the most important design decision in the codebase. It is recorded as docs/adr/0001-database-is-the-single-source-of-truth.md.

  Sync ─────┐                                      ┌──► LibraryModel ──► LibraryView
            │ write                       observe  │
  Downloads ┼──────►  SQLite (AppDatabase)  ───────┼──► BookDetailModel ──► BookDetailView
            │          ValueObservation            │
  Player ───┘                                      └──► DownloadsModel ──► DownloadsView
     │
     └── live position (4×/s) ─────────────────────────► player views read the Player directly
  • Background work (Sync, Downloads, Playback) only writes to the database. It returns simple outcome values and never holds a reference to a screen.
  • Each screen's @MainActor @Observable model reads synchronously in its init, so the very first frame shows real rows, not a spinner. It then observes the same query (fooUpdates(), a ValueObservation under the hood) in a loop that the view starts with .task. Store pairs every read this way: foo() and fooUpdates() share one fetch function.
  • Why: persistence was a primary goal. What the UI shows is already on disk, so killing the app loses nothing, and there is no second, in-memory copy of the state that could drift from the saved one. The rejected alternative was shared in-memory models at the app root with the database behind them, which would have meant two sources of truth and explicit wiring for background work to reach the UI.
  • The exception is the live playback position, which changes several times a second. The Player is itself @Observable and exposes it directly. It writes the position to the database every second while playing, and straight away on play, pause, seek, skip, the end of a Book and going to the background.
  • A second, smaller exception: Broadcast in Store is an in-memory fan-out for two events that a table can't show after the fact: "progress was adopted from the Server" (so the Player can offer a pick-up notice) and "Downloads were deleted by sync" (so the Downloader can cancel their transfers).

When you add a feature, the default shape is: the worker writes a row, the screen model observes it. If you find yourself passing a callback from a worker to a view, stop and re-read the ADR.

The composition root and launch

There is no dependency-injection framework and no singletons inside the modules. Everything is created in one place, Services.init in [[Logos/LogosApp.swift]], and passed down through initializers. This is called plain initializer injection. In order:

  1. Choose the launch environment ([[Logos/LaunchEnvironment.swift]]). Normally that is Application Support, the real AudiobookshelfClient and the Keychain. In Debug and Performance builds a LOGOS_TEST_LAUNCH variable can swap in test data and a FakeServer ([[Logos/TestLaunch.swift]]).
  2. Open the database at Logos.sqlite. If that fails, the app shows DatabaseErrorView and keeps the file. It never deletes data automatically. Then it closes any listening session that a previous kill left open.
  3. Create SignIn, the Covers/ and Downloads/ directories, one Player (with the system audio player and audio session) and one NowPlaying for the lock screen. These live for the whole process and survive sign-ins.
  4. If a Server identity is saved (that is what "signed in" means), create that identity's Downloader and start it. A background launch to handle finished transfers has no UI, so this has to happen here.
  5. Per-identity objects (one Auth and one Downloader) are created lazily by shared(for:) and shared by everything that needs them, so there is only ever one token refresh in flight. Signing out drops them.

The background URLSession for Downloads is a static let created as early as possible. When iOS wakes the app for finished transfers, the session has to exist to receive the events ([[#primer-background]]).

In the UI, AppRootView creates a LaunchModel. It reads the identity synchronously and either shows sign-in or builds every per-identity screen model at once (Library, In Progress, Series, Downloads, Settings, the listening reporter, sign-in-again, sign-out). RootView then waits until the first frame is on screen (FrameShown, a short CADisplayLink) before it starts anything slow: the cover file check, the Downloads check and resume, and a sync. The player restores the last-played Book, paused, after that frame too.

House rule

Nothing on the launch path touches the network or runs the file check. The cold-launch budget is 400 ms with 3000 Books. Even creating an AVPlayer eagerly was measured at 10–60 ms, so it is created lazily.

Seams: how the code is made testable

A seam is a place where you can swap the real thing for a test double without changing the code that uses it. In Logos each seam is a protocol, and the fake lives in the module's own sources (not in the test target). That way other modules' tests and the app's test launches can use the fake too.

Two more shared tools in Domain: Diagnostics.logger(_:) (each module has a log with its own LogCategory; logs never include hosts, tokens or bodies) and Signposts, which marks each budgeted path for the performance tests ([[#performance]]).

Who runs where

  • Main actor: the whole UI module, the whole Playback module and the app target (configured as main actor by default). The Player is main-actor because SwiftUI reads its position directly. Pure value types in those modules opt out with nonisolated.
  • Actors for background workers: LibrarySync, ProgressSync, SessionOutbox, Connection, Downloader and Auth. A common pattern: when a request arrives while a run is in progress, it joins that run instead of starting a second one (and the Outbox sets sendsAgain so the latest state always goes out).
  • The database is a DatabasePool (WAL mode): many concurrent readers and one writer. Writes are transactions. A related group of changes, such as "save position, extend the listening session, queue a Finished change", happens in one transaction.
  • Expensive UI work, such as rebuilding the Library's sort and search index, runs in a detached task. A generation counter throws away results that a newer rebuild has replaced.

Journey: signing in

  1. SignInView → SignInModel.submit → SignIn in Sync ([[Sync/SignIn.swift]]).
  2. GET /status: the Server must be 2.36.0 or newer and allow local sign-in. Only HTTPS is accepted. Test launches may allow plain HTTP to loopback.
  3. POST /login, then fetch the Libraries, ignoring podcast Libraries. With none it is an error, with one it is picked automatically, and with several the user chooses.
  4. choose saves the tokens to the Keychain first and then the ServerIdentity row. If the app is killed in between, the user is simply not signed in yet. A login the app decides not to keep is logged out on the Server again.
  5. Nobody "navigates" to the Library. LaunchModel is observing the identity, sees the new row and swaps the sign-in screen for the tab shell. This is the single-source-of-truth pattern again.

Later, if a token refresh is rejected, Auth reports needs sign-in. Connection publishes it, and a banner offers "Sign In Again", which must be the same Server and the same user.

Journey: a sync

Sync runs on launch (after the first frame), on returning to the foreground (a full sync only if the last one was more than 15 minutes ago, though progress is fetched every time) and when the user pulls to refresh. LibrarySync ([[Sync/LibrarySync.swift]]) goes through these steps in order:

  1. Version check, every time. If the Server is too old, sync stops and the UI says so.
  2. Stage 1, the Library list: the whole list of [[term:Book]]s, applied in one transaction. Books the Server no longer lists are deleted, unless they are downloaded, in which case they become [[term:Not on Server]] and stay playable. An empty list is never applied, and the list's decoding is strict: a list read only partly would wrongly mark Books as gone.
  3. Progress fetch ([[Sync/ProgressSync.swift]]): the Server's progress is merged last-writer-wins on when the listener acted (ProgressMerge in Domain). A Book with anything in the [[term:Outbox]] is never overwritten.
  4. Stage 2, full Book data (Chapters, audio files, Series) for Books whose data is behind, 50 at a time with one transaction per batch, so an interrupted sync picks up where it stopped.
  5. Stage 3, covers, four at a time.

The Outbox: sending listening back

The Player records [[term:Listening session]]s and [[term:Finished change]]s in the database. ListeningReporter (UI) triggers SessionOutbox.send on launch, every 60 seconds while playing, on pause, on each Finished change, on going to the background, when the network comes back, and once more before sign-out. A send works like this:

  1. Close sessions that have been paused too long.
  2. If there are Finished changes, fetch progress first, so an older local change doesn't overrule a newer one from another device.
  3. Send sessions in batches of 100 (POST /api/session/local-all). Each one is confirmed at the revision that was sent, so a session that kept growing in the meantime is sent again.
  4. Send Finished changes.
  5. Fetch progress again.

Sends are fire-and-forget: playback never waits for them, and a failed send is simply retried at the next trigger.

Journey: downloading a Book

  1. DownloadButton → DownloadsModel.startDownload → Downloader.download ([[Downloads/Downloader.swift]]), which queues a row in the database. The queue lives in the database, so it survives a kill.
  2. Books download one at a time, first in first out. To start a Book, the Downloader:
    • makes sure the token has at least 10 minutes left (a background transfer can't refresh mid-request);
    • re-reads the Book's file list, matching files by path;
    • checks storage (remaining bytes plus 500 MB, otherwise the queue pauses as "Not enough storage");
    • marks files that are already complete as verified, and hands the rest to the background session, with resume data where it has it.
  3. Transfers continue while the app is suspended or killed. Each task's description carries enough JSON to reconnect it to its Book after a relaunch. The file must be moved out of the system's temporary location during the "finished downloading" callback, before URLSession deletes it.
  4. A file is verified when the status is 200/206 and its size on disk equals the Server's size. The failure rules: a 401 refreshes the token, a 403 fails the Book, a 404 retries once after re-reading the Book, a wrong size is fetched again once, and anything else backs off for 1, 5 and then 30 minutes, up to 5 attempts.
  5. A [[term:Download]] counts as downloaded only when every file and the cover are present and verified. Wi-Fi only, unless the user allows cellular.
  6. The UI never hears from the Downloader directly. DownloadsModel observes the download tables.

Journey: playing

  1. PlayButton → Player.play(bookID:) ([[Playback/Player.swift]]). The Player checks that the Book is downloaded and intact, loads its files into one AVPlayer timeline (player time = Book time), seeks to the saved position and plays. A loadGeneration counter discards a load that finishes after a newer one began.
  2. While playing, the Player publishes the position about 4 times a second and saves it once a second. Each save also extends the current [[term:Listening session]], in the same transaction.
  3. Seeking moves position immediately and the audio catches up. That is how "seek → UI in the same frame" is met.
  4. Stopping always has a reason (pause, switched Book, Sleep Timer, interruption, …). The reason decides whether the listening session ends. Stopping or skipping within the last 30 seconds marks the Book [[term:Finished]] (FinishRule), though a pause the system causes never does, and playing a Finished Book again starts it from the beginning.
  5. The [[term:Sleep Timer]] counts Chapters, not minutes. It pauses at the end of the Xth Chapter.
  6. Interruptions: a phone call pauses, and playback resumes afterwards only if iOS recommends it. Unplugging headphones pauses and never resumes. If the system's media services reset, the AVPlayer is rebuilt.
  7. Pick up: if a sync adopts newer progress from another device for the paused Book, the Player moves to it and offers Undo.
  8. NowPlaying keeps the lock screen and Control Center in step, showing the current Chapter as the title.

Journey: signing out

SignOutModel ([[UI/SignOutModel.swift]]) is a small state machine:

  1. Pause playback and send the Outbox.
  2. Ask for confirmation, showing what will be lost (number and size of Downloads, any unsent listening).
  3. Stop the player and Downloads, sign out of the Server, delete covers and Download files.
  4. database.wipe() empties every table. This is the only place data is deliberately deleted.
  5. The identity row is gone, so LaunchModel falls back to sign-in, and the app drops its Auth and Downloader so a new sign-in builds fresh ones.

The main tables, all defined in Store:

  • serverIdentity: the Server, user and Library. Having this row is being signed in.
  • syncState: when the last sync ran, and whether the Server is too old.
  • book, chapter, audioTrack, bookSeries: the Library. There is no Series table: Series are derived from bookSeries.
  • progress: position, Finished, and lastChanged (when the listener acted, never when the data was sent or fetched).
  • download, downloadFile, downloadPolicy: the queue, per-file state including resume data, and the cellular and storage rules.
  • listeningSession, finishedChange: the Outbox.
  • playbackSettings, clientDevice.

Some details that surprise people:

  • progress, listeningSession and finishedChange have no foreign key to book. Local listening deliberately survives a Book leaving the Library.
  • Times compared with the Server's are stored as integer milliseconds.
  • There is no "not downloaded" state: no download row means no Download.
  • Migrations are hand-written, append-only, and never edited after they ship.

Performance budgets

Performance is a requirement with numbers, written down in docs/performance-budgets.md and measured on an iPhone 15 Pro with a Release build:

PathMedian budget
Cold launch → interactive Library (940 and 3000 Books)≤ 400 ms (worst ≤ 700 ms)
Search keystroke → updated list (3000)≤ 50 ms
Sort change, letter-index jump, tap Book → detail≤ 100 ms
Play another downloaded Book → audio≤ 500 ms
Seek / skip → UIsame frame
Scrolling any list< 5 ms/s hitches
Memory while browsing≤ 150 MB

How the code meets them:

  • Screens read synchronously in init, so there is no loading state on the first frame.
  • All slow work waits for the first frame.
  • LibraryCatalog pre-sorts and pre-folds the search text once per data change, so a sort change is a lookup and a keystroke is one linear pass, with no full-text index.
  • Cover thumbnails are decoded off the main thread into a bounded cache.

Each budgeted path is wrapped in a signpost (Signposts.measure or begin/end with a BudgetedPath case), which the XCUITest performance tests measure. A PR that touches one records iPhone numbers. When persistence and performance conflict, persistence wins.

Decisions in brief

Only the database decision is recorded as an ADR so far. The rest are visible in the code, CLAUDE.md and the glossary. A new decision worth remembering (or a new dependency) gets an ADR in docs/adr/.

DecisionWhat it means for you
Play only from complete, verified DownloadsPlayback can't import the network layer. Anything "online" belongs in Sync or Downloads.
The database is the single source of truth (ADR 0001)Workers write rows and screens observe them. Nothing is lost on a kill.
A local Swift package of modules with an enforced graphA wrong import fails the build or CI.
Plain initializer injection in one composition rootAll the wiring is in [[Logos/LogosApp.swift]]. To add a long-lived object, add it there and pass it down.
Hand-written fakes next to the real codeReuse FakeServer, TestClock and the other fakes. Extend them rather than adding a mocking library.
GRDB and Apple frameworks onlyA new dependency needs an ADR, and builds resolve only from the checked-in Package.resolved.
Progress is merged last-writer-wins on when the listener acted, and unsent local changes are never overwrittenKeep lastChanged meaning "when the listener acted", never "when it was sent or fetched".
The Sleep Timer counts ChaptersIt is defined that way in the glossary. There is no minutes countdown.

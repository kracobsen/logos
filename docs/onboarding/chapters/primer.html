iOS & Swift primer

The platform ideas this codebase depends on, explained from the ground up, with pointers to where Logos uses each one.

This chapter assumes you can program, but not that you have written an iOS app. Each section explains just enough to read the code. The annotated pages explain the details when they first come up.

Swift in ten minutes

Swift is a compiled, statically typed language. Some features matter in every file:

  • struct vs class. A struct is a value: assigning it copies it, like an Int. A class is a reference: two variables can point at the same object. Logos uses structs for data (a Book, a Chapter, a Progress, all in Domain) and classes for long-lived things with identity (the Player, screen models). final class just means "nobody may subclass this".
  • let and var. let is a constant and var can change. On a struct, a mutating func is a method that changes the value.
  • Optionals. String? means "a String, or nil". You must unwrap it before use: if let name { … }, guard let name else { return }, name ?? "default", or name! (crash if nil; rare here). guard is an early exit: "make sure this is true, otherwise leave now".
  • enum with associated values. Swift enums can carry data per case, e.g. case failed(reason: String). A switch over an enum must handle every case, so the compiler tells you about every place to update when you add one. Logos uses this a lot for state ("signed out / signing in / signed in").
  • Protocols. A protocol is an interface. Code that says any ServerAPI works with any type that implements the ServerAPI protocol: the real HTTP client in the app, a fake in tests. Most of the "seams" in this codebase are protocols ([[#seams]]). some View is the opposite direction: "one specific type that I won't name". SwiftUI uses it a lot.
  • Extensions. extension Player { … } adds methods to a type, often in another file. Logos splits big types this way: Player.swift plus Player+SleepTimer.swift, Player+Sessions.swift and so on. The Type+Topic.swift file name is the convention.
  • Access control. public means visible to other modules. Without a keyword, a symbol is internal: visible only inside its own module. private means visible only in the enclosing declaration and file. Because each module is a separate Swift module, public marks a module's interface on purpose.
  • Codable. A type that conforms to Codable can be turned into JSON and back, mostly automatically. ServerAPI decodes the server's JSON this way.
  • Doc comments. /// comments are documentation that Xcode shows on hover. The code uses them a lot, and they are usually the best explanation of intent.

SwiftUI: describing the screen

SwiftUI is Apple's declarative UI framework. You never move buttons around by hand. Instead, you write a function of state that describes what the screen should look like, and SwiftUI works out what to change when the state changes.

struct GreetingView: View {
    let name: String
    var body: some View {          // "what this view looks like right now"
        VStack {                   // stack children vertically
            Text("Hello, \(name)")
            Button("Play") { … }   // the closure runs on tap
        }
        .padding()                 // a "modifier" wraps the view in another view
    }
}
  • Views are small, cheap structs. SwiftUI rebuilds them often, so they should not hold long-lived state themselves.
  • body uses a result builder: the list of views inside the braces is collected automatically, and if and switch work inside it.
  • @State is a property wrapper for small local state that a view owns (is a sheet showing, what is in a text field). @Binding passes write access to someone else's state. @Environment reads values passed down the view tree.
  • .task { … } runs async work while a view is on screen and cancels it when the view goes away. Logos uses this to start the database observations that feed each screen.
  • Navigation uses TabView (the tabs along the bottom), NavigationStack (push and pop), and .sheet (cards that slide up, such as the player).

An app starts at a type marked @main that conforms to App. Its body is a Scene, usually a WindowGroup holding the root view. In Logos that is [[Logos/LogosApp.swift]].

@Observable models

Screens in Logos follow a model + view pattern. Each screen has an @Observable class, for example LibraryModel or BookDetailModel, that holds the screen's data and its actions. The view reads the model's properties in body.

@Observable is a macro (code generated by the compiler). It records which properties each view read while drawing, and redraws only those views when one of those properties changes. You don't need @Published, Combine or manual "notify" calls: assigning a property is enough.

Where does the model get its data? Not from other objects telling it. It observes the database. See [[#single-source-of-truth]]. This makes the screen models in Logos thin: mostly "observe query X and put the result in property Y", plus methods that write to the database or call into Sync, Downloads or Playback.

async/await and tasks

Anything slow (network, disk, waiting) is written with async/await:

func fetchBooks() async throws -> [ListedBook] {
    let data = try await api.send(request)   // suspends here without blocking the thread
    return try decode(data)
}
  • async means the function can suspend. await marks each point where it might suspend. throws/try is Swift's error handling (errors are values that are thrown, not exceptions that unwind through anything).
  • A Task { … } starts concurrent work. It can be cancelled, and well-behaved code checks for cancellation. In tests, cancellation shows up as a thrown CancellationError.
  • for await value in stream loops over an AsyncSequence, a series of values that arrive over time. Database observations and timers are exposed this way. For example, Clock.timer(every:) in [[Domain/Clock.swift]] is an AsyncStream of ticks.

Actors, the main actor and Sendable

Swift 6 checks for data races when it compiles. Two rules cover most of what you will see:

  • An actor is like a class whose state only one task can touch at a time. Calls from outside are awaited. In Logos, the long-running background workers are actors: LibrarySync, ProgressSync, SessionOutbox, Connection (in Sync) and Auth (in ServerAPI, so two token refreshes never run at once).
  • @MainActor is the one special actor: the main thread, where all UI work must happen. The UI and Playback modules, and the app target, are compiled with main actor by default, so everything in them runs on the main thread unless it says otherwise (nonisolated). That keeps UI code simple. Heavy work such as database reads runs elsewhere and hands its results back.
  • Sendable marks a type as safe to pass between concurrent contexts. Immutable structs usually are. A mutable class usually is not. When the compiler complains that something "is not Sendable", it has found a possible race.
House rule

The project uses Swift 6 language mode with complete strict concurrency, and warnings are errors, so a possible data race fails the build. Fix the cause rather than silencing it: the code uses the nonisolated(unsafe) escape hatch in only three places, each to hand a system-provided completion handler across an isolation boundary (one is the app delegate in [[Logos/LogosApp.swift]]).

Swift packages and modules

A Swift package is a folder with a Package.swift manifest that declares targets. Each target is a separate module, compiled on its own, with its own namespace and its own public interface. A target can use another only if the manifest lists it as a dependency and the file says import ThatModule.

Logos puts almost everything in one local package, LogosKit/, with seven targets (Domain, ServerAPI, Store, Sync, Downloads, Playback, UI). Splitting it this way lets the compiler and a check script enforce the architecture: if Playback tries to import ServerAPI, the build or CI fails. See [[#module-graph]]. Dependencies are pinned in Package.resolved, which is checked in.

Xcode projects, targets, schemes and configurations

  • Project (Logos.xcodeproj): Xcode's description of what to build. In this repo it contains almost nothing: one app target, one UI-test target, and a reference to the local package.
  • Target: one product, such as the app or a test bundle.
  • Configuration: a named set of build settings. Logos has Debug (for development), Release (what ships) and Performance (Release optimisation plus test hooks, for measuring).
  • xcconfig files (Config/*.xcconfig): build settings as plain text instead of hidden in the project file. Settings are kept in these files so that changes are easy to review.
  • Scheme: "build these targets with this configuration, and run or test with these options". The schemes are Logos (app plus all unit tests), LogosUITests and LogosPerformance.
  • Info.plist and entitlements declare things to iOS: the app's name, that it may play audio in the background, and so on.
  • Simulator vs device. The Simulator runs on your Mac and is good for most work. Battery, background audio, lock screen and real performance need a physical iPhone. See [[#house-rules]].

xcodebuild is Xcode's command-line build tool. The scripts/ wrap it so you rarely type it yourself.

Apps in the background

An iOS app is not a normal long-running process. When the user leaves it, iOS suspends it within seconds, and it may kill the app later without warning. Two exceptions matter to Logos:

  • Background audio. Because Info.plist declares the audio background mode, the app keeps running while it is playing sound. When playback stops, it can be suspended again.
  • Background URL sessions. A URLSession with a background configuration hands downloads to a system process. They continue while the app is suspended, or even after it has been killed. When they finish, iOS launches or wakes the app and calls application(_:handleEventsForBackgroundURLSession:completionHandler:). That is why [[Logos/LogosApp.swift]] creates the transfers object as early as possible, and why the Downloads code must cope with learning about finished files after a relaunch.

Because the app can be killed at any moment, it saves state as it goes. That is the main reason for the database-first design.

Audio: AVFoundation and Now Playing

  • AVPlayer plays media. Logos builds a queue of a Book's local audio files and plays them at the chosen speed, with the time-domain pitch algorithm so sped-up speech still sounds natural.
  • AVAudioSession tells iOS what kind of audio the app makes ("spoken audio playback") and reports interruptions (a phone call) and route changes (headphones unplugged, which should pause).
  • Now Playing and remote commands (MPNowPlayingInfoCenter, MPRemoteCommandCenter): what the lock screen, Control Center and headphone buttons show and control.

Each of these is wrapped behind a small protocol (AudioPlayer, AudioSession, NowPlayingCenter) with a System… version for the app and a Fake… version for tests. See the Playback page.

SQLite and GRDB

GRDB is the project's only third-party dependency. It is a Swift library for SQLite. The parts used here:

  • DatabasePool: one database file that allows many readers at once and one writer. Reads and writes are closures: try pool.read { db in … }, try pool.write { db in … }. A write is a transaction: it all happens or none of it does.
  • Records: structs that conform to GRDB protocols (FetchableRecord, PersistableRecord) can be read from and written to tables without hand-written SQL. Raw SQL is still used where it is clearer or faster.
  • Migrations: numbered, append-only schema changes. The database on a user's phone is upgraded step by step on launch. You never edit a migration that has shipped. You add a new one.
  • ValueObservation: "run this query now, and again whenever a table it read from changes". This is how every screen stays up to date. Logos wraps it in one helper, observe(_:) in [[Store/AppDatabase.swift]], which returns an async sequence of results with duplicates removed.

Testing tools

  • Swift Testing (import Testing) is used for all unit tests. A test is a function marked @Test, and checks are written #expect(a == b) or try #require(x). A @Suite groups tests. Tests can be async.
  • XCTest / XCUITest is the older framework. It is still needed for UI tests, which launch the real app and tap through it like a user, and for performance tests (measure(metrics:)). Those live in LogosUITests/.
  • Fakes over mocks. Instead of a mocking library, the code ships hand-written fakes next to the real implementations: FakeServer, FakeFileTransfers, FakeAudioPlayer, TestClock. Tests use the real database (a temporary file) rather than faking it.

More in [[#tests]] and on the Tests page.

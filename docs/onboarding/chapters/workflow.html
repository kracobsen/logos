Working in the repo

Setup, the checks CI runs, the kinds of tests and when to run each, and the rules a pull request has to meet.

Getting set up

  1. Install an Xcode that ships the iOS 27 SDK and open it once so it can install its components. If xcode-select -p prints a CommandLineTools path, either run sudo xcode-select -s /Applications/Xcode.app or prefix Xcode commands with DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer. The scripts set it for you.
  2. Open Logos.xcodeproj, pick the Logos scheme and an iPhone simulator, and press ⌘R. You don't need to configure anything to run in the Simulator. Xcode resolves GRDB from the checked-in LogosKit/Package.resolved.
  3. To run on a real iPhone, copy Config/Local.xcconfig.template to Config/Local.xcconfig (it is git-ignored) and fill in your own team ID and bundle-ID prefix. The README walks through Developer Mode and trusting the certificate. Never put signing settings in the project file.
  4. To sign in you need an audiobookshelf Server over HTTPS, because normal builds refuse plain HTTP. To try things locally without one, run scripts/integration-test.sh --serve (needs Docker). It starts a throwaway Server on 127.0.0.1 and prints its address. Debug builds launched with LOGOS_TEST_LAUNCH=signedOut are allowed to sign in to it over plain HTTP. See [[Logos/TestLaunch.swift]].
  5. Install Docker only if you will run the integration or UI smoke tests.
iOS & Swift

Where to find things in Xcode: the Project navigator (⌘1) shows files; LogosKit shows up there as a package, and you can open any module's sources from it. Product › Test (⌘U) runs the scheme's tests; the diamond next to a @Test runs just that one. ⌘-click a symbol to jump to its definition; ⌥-click shows its doc comment.

The three checks CI runs

.github/workflows/ci.yml runs these on every pull request and on every push to main. Run them yourself before pushing:

Unit tests

Each module has a test target named <Module>Tests in LogosKit/Tests/, written with Swift Testing. They are fast and run without a network. The main techniques, all shown on the Tests page:

  • A real database in a temporary directory. Tests open AppDatabase on a fresh file instead of mocking the Store, so the SQL and migrations are tested too.
  • TestClock instead of real time. Code in Sync, Downloads and Playback gets the time and sleeps only through the injected Clock, so a test can say "advance 10 minutes" and check that a [[term:Listening session]] ended, without waiting.
  • Fakes for every outside system: FakeServer (an in-memory audiobookshelf), FakeFileTransfers, FakeAudioPlayer, FakeAudioSession, FakeNowPlayingCenter, InMemoryTokenStore. They live in the module's own sources, next to the real implementation, so tests in other modules and the test launches can use them too.
  • Recorded server JSON in Tests/ServerAPITests/Payloads/, to check decoding against what audiobookshelf really sends.

Integration tests (against a real Server)

scripts/integration-test.sh runs the IntegrationTests target against a real audiobookshelf. Here is what it does:

  1. Generates a small fixture Library of audio files (scripts/integration/make-fixture-library.sh).
  2. Starts audiobookshelf 2.37.1, pinned by image digest, in Docker on a free loopback port, with no persistent volume.
  3. Seeds it with an admin root/rootpass, a user listener/listenerpass and one book Library called "Fixtures".
  4. Runs the tests, fails if any test was skipped, and removes everything afterwards.
House rule

Never point integration tests at a real Server. IntegrationServer.current() refuses any address that is not loopback. The credentials above belong only to the throwaway container. CI does not run these tests (it has no Docker), so a PR that touches ServerAPI or Sync attaches the integration test result in its description.

Without the harness running, the integration tests skip rather than fail. That is why IntegrationTests is outside the Logos scheme and scripts/test.sh doesn't run it. Pass xcodebuild arguments through to narrow it, e.g. scripts/integration-test.sh -only-testing:IntegrationTests/HarnessTests.

UI tests, test launches and performance tests

LogosUITests/ holds XCUITest tests that launch the real app:

  • The smoke test (SmokeTests, scheme LogosUITests): sign in, browse, download, play, against the Docker Server. Run it with scripts/integration-test.sh --ui. KEEP_RESULTS=<dir> keeps the .xcresult bundle so you can look at screenshots and logs.
  • Performance tests (*PerformanceTests, scheme LogosPerformance, the Performance configuration). They measure the budgets on a physical iPhone 15 Pro. Simulator numbers don't count. The procedure is in docs/performance-budgets.md, and scripts/perf-results.sh prints the medians from a result bundle.

Both rely on test launches. Builds compiled with the LOGOS_TEST_LAUNCH condition (Debug and Performance, never Release) read the LOGOS_TEST_LAUNCH environment variable at launch:

  • signedOut: fresh empty data on every launch, and plain HTTP allowed to a loopback Server.
  • library940 / library3000: already signed in to an offline FakeServer holding a generated FixtureLibrary of that many Books, with covers, progress and a few downloaded Books with real (silent) audio.

UI tests find elements by what the listener sees, such as button labels and tab titles, not by internal identifiers. That way the tests keep passing when the layout changes.

Pull requests

Work is tracked in GitHub Issues on kracobsen/logos. Larger features usually start as a spec issue (look for spec-NN branch names). Before you open a PR, check the following:

  • The three CI checks pass locally.
  • New behaviour has tests in the right module's test target.
  • If the PR touches ServerAPI or Sync, attach the result of scripts/integration-test.sh.
  • If the PR touches a budgeted path (launch, scrolling, search, sort, play, seek, sync…), record iPhone measurements next to the budget in the description. A breach blocks the merge unless the PR also changes docs/performance-budgets.md with a written reason.
  • If the PR touches device-only behaviour, the description must include a manual checklist that the human signs off before merge. Device-only behaviour means interruptions and audio routes, the lock screen and Control Center, background Downloads and surviving a reboot, listening at 1×, 2× and 3×, battery, and smoothness.
  • If the PR adds a dependency, it also adds an ADR in docs/adr/. Only GRDB and Apple frameworks are allowed today.
  • If the PR changes the module graph, it changes Package.swift, scripts/check-module-graph.sh and the table in CLAUDE.md together.
  • If the PR introduces new domain words, it updates GLOSSARY.md. If it makes an architectural decision worth remembering, it adds an ADR.

House rules, collected

These are spread across CLAUDE.md, the ADR and the budgets document. Here they are in one place:

RuleWhy
Build settings live only in Config/*.xcconfig. Structural changes (targets, dependencies) happen only in LogosKit/Package.swift. Never edit either through the project file.Project files are hard to review and merge. Text configs and a Swift manifest are easy to read in a diff.
Respect the module graph. In particular, Playback never imports ServerAPI, only Store imports GRDB, and nothing depends on UI.See [[#module-graph]].
Sync, Downloads and Playback write to the database and never call into the UI. The UI observes the database.ADR 0001, see [[#single-source-of-truth]].
Never call Date() or Task.sleep in Sync, Downloads or Playback. Use the injected Clock.Makes time-based behaviour testable with TestClock.
Log through Diagnostics.logger(_:), with each module's own log and LogCategory.One consistent place to filter logs in Console.app.
Mark budgeted paths with Signposts. A new budget gets a new BudgetedPath case.Performance tests and Instruments measure exactly those intervals.
Nothing on the launch path touches the network or runs the file check.The cold-launch budget is 400 ms.
Persistence wins over performance when the two conflict.Losing a listener's place is worse than being slow.
The database is never deleted automatically, even if it fails to open.The app shows an error screen and keeps the file ([[Logos/LogosApp.swift]]).
